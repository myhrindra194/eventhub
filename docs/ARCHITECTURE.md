# EventHub — Architecture

Feature-first, clean-layered Flutter application. Every feature owns its
layers; cross-cutting code lives in `core/`, navigation in `routes/` and app
wiring in `app/`. The French, product-level overview is in the root
[`README.md`](../README.md); this document is the technical reference.

```
lib/
├── main.dart · main_dev.dart · main_staging.dart · main_prod.dart   entrypoints
├── bootstrap.dart              startup sequence (Firebase or mock, error handlers, ProviderScope)
├── firebase_options.dart       generated by flutterfire (git-ignored; stub by default)
├── app/
│   ├── app.dart                MaterialApp.router, fr_FR locale, light + dark themes
│   └── theme/                  "Aurora" design system: palette, tokens, spacing & radii,
│                               typography, motion, ThemeData builder, ThemeModeController
├── routes/                     AppRoutes (paths, names, builders), RouteGuard (pure policy),
│                               AppPage/AppTransition, route observer, appRouterProvider
├── core/
│   ├── config/                 Flavor, AppConfig (MOCK, USE_EMULATORS), Clock, AppLinks
│   ├── errors/                 Failure hierarchy, ErrorMapper, FailureException
│   ├── result/                 Result<T> (Ok/Err), guard()
│   ├── firebase/               SDK providers, collection/field names, converters
│   ├── mock/                   MockStore (seeded demo data) + mock repository implementations
│   ├── l10n/                   AppStrings (FR)
│   ├── utils/ · extensions/    logger, validators, date formats, context helpers
│   └── widgets/                component library, re-exported by design_system.dart
└── features/
    ├── onboarding/             first-launch carousel, seen-once flag
    ├── auth/                   sign-up (2 steps), sign-in, session, profile, edit profile,
    │                           settings, password change / reset
    ├── events/                 catalogue, search & filters, detail, create/edit form, share sheet
    ├── reservations/           transactional booking, confirmation, wallet, ticket (QR)
    ├── organizer/              organizer shell, dashboard, statistics, alerts, participants
    │                           + CSV export, "event published"
    ├── participant/            participant shell (Explorer · Recherche · Billets · Profil)
    └── support/                help centre, privacy notice, about (presentation only)
        └── <feature>/
            ├── domain/         entities (freezed), policies, pure calculators, repository interfaces
            ├── data/           DTOs, Firestore/Storage data sources, repository impls
            ├── application/    Riverpod providers & controllers (use-cases)
            └── presentation/   screens & widgets
```

A feature only has the layers it needs: `support/` is pure presentation,
`organizer/` has no `data/` of its own because it composes the `events` and
`reservations` repositories.

## Dependency rule

```
presentation ──▶ application ──▶ domain ◀── data
                                    ▲
                                    └── core/mock (demo implementations)
```

* `domain` depends on nothing but `core/result` and `core/errors`.
  No Flutter, no Firebase (`TimeOfDayValue` exists for that reason).
* `data` implements domain interfaces; it is the only layer that imports
  `cloud_firestore` / `firebase_auth` / `firebase_storage`.
* `application` composes repositories into providers. Controllers expose
  `Future<Result<T>>` **and** mirror the in-flight state in `AsyncValue`
  so screens can both `await` the outcome and render loading/error.
* `presentation` reads providers and never touches repositories directly.
* A feature never imports another feature's `data` layer. Importing another
  feature's `application` providers (organizer → events, reservations) is
  allowed.

## Error handling

Repositories never throw. Every method returns `Result<T>`:

```dart
switch (await repo.reserve(...)) {
  case Ok(:final value): ...
  case Err(:final failure): context.showFailure(failure);
}
```

`guard()` is the single try/catch: it maps SDK exceptions through
`ErrorMapper` into the sealed `Failure` hierarchy (`AuthFailure`,
`NetworkFailure`, `PermissionFailure`, `NotFoundFailure`,
`ValidationFailure`, `BusinessRuleFailure`, `StorageFailure`,
`UnexpectedFailure`). Inside Firestore transactions, domain rule violations
are thrown as `FailureException(failure)` and unwrapped by `guard()`.

## Business rules (domain policies)

| Rule (spec §7)                                   | Where enforced                                  |
|--------------------------------------------------|-------------------------------------------------|
| One reservation per participant per event        | `ReservationPolicy` + deterministic doc id `<eventId>_<uid>` + rules |
| No booking on a full event                       | `ReservationPolicy.canReserve` (in transaction) + rules bound check |
| No booking once the event started                | `ReservationPolicy.canReserve`                  |
| `availablePlaces` updated per reservation        | Firestore transaction (`FieldValue.increment`)  |
| Organizer edits/deletes only own events          | `EventPolicy.canManage` + `firestore.rules`     |
| Capacity cannot drop below reservations          | `EventPolicy.availablePlacesAfterCapacityChange` (in transaction) |
| Profile: only the display name can change        | `AuthRepository.updateProfile(name)` + rules (`onlyChanged(['name', …])`) |
| Reservation lists expose only the caller's data  | queries filter on `userId` / `organizerId` + list rule proves it |
| Deleted event no longer bookable                 | Hard delete; reservations keep denormalised event data |

Policies are pure Dart and fully unit-tested (`test/features/*/domain`).
They run **inside** the Firestore transaction so two concurrent bookings of
the last seat cannot both succeed. `firebase/firestore.rules` re-checks the
invariants server-side for tampered clients.

### Pure calculators

Some domain code computes rather than decides. They follow the same rule —
pure, framework-free, unit-tested:

| Calculator | Input → output |
|---|---|
| `Reservation.ticketCode` / `ticketPayload` | reservation id → `EH-XXXX-XXXX` + QR payload (FNV-1a, stable across platforms) |
| `GuestListCsv.build` | reservations → RFC 4180 CSV, `;` separator (French Excel) |
| `OrganizerStats.compute` | events + reservations + now → fill rate, 14-day timeline, cancellations, ranking |
| `OrganizerAlerts.watchlist` / `activity` | events / reservations → "à surveiller" list and bookings/cancellations journal |

Organizer statistics are derived on the client from two streams already
open (`watchByOrganizer` on events and reservations). No aggregate document,
no Cloud Function — the limits (at most 200 reservations, a cancelled then
re-booked seat is one document) are written in `organizer_insights.dart`.

## Authentication session

`authSessionProvider` (kept alive) exposes a sealed `AuthSession`:

* `SignedOut`
* `SignedIn(AppUser)` — Firebase user **and** Firestore profile present
* `ProfileMissing(uid, email)` — account without profile document; the
  router sends it to `/complete-profile`. A grace period
  (`AppConfig.profileGracePeriod`) absorbs the sign-up window between
  `createUser` and the profile write.

The router's `refreshListenable` is notified on every session change, so
role-based redirects run without rebuilding `GoRouter`. A profile update
flows back through the same stream: no screen has to refresh the user.

## Navigation

`routes/` is self-contained; features import `routes/routes.dart` only.

* Two `StatefulShellRoute`s — participant (4 tabs) and organizer (4 tabs:
  Événements · Stats · Alertes · Profil) — each tab keeping its own stack.
* Leaf routes (detail, ticket, forms, participants, support pages) sit on
  the root navigator so they cover the navigation bar.
* `RouteGuard.redirect` is a pure function of `RouteGuardState`: booting,
  first launch, signed out, profile missing, role confinement. Pages both
  roles share (`/welcome`, `/change-password`, `/account/edit`, `/help`,
  `/privacy`, `/about`) are declared role-agnostic in `AppRoutes`.

## Data model (Firestore)

```
users/{uid}                 name, email, role, createdAt, updatedAt?
events/{id}                 title, description, imageUrl?, category, startsAt,
                            location, capacity, availablePlaces,
                            organizerId, organizerName, createdAt, updatedAt
reservations/{eventId_uid}  eventId, userId, organizerId, userName, userEmail,
                            eventTitle, eventStartsAt, eventLocation,
                            status (confirmed|cancelled), reservedAt, cancelledAt?
```

Design decisions:

* `date` + `time` from the spec are stored as one `startsAt` Timestamp
  (exact ordering, "upcoming" query, "already started" rule). The `Event`
  entity exposes `date` / `time` views.
* Reservations denormalise user and event fields: the participant list and
  the wallet render with a single query and survive event deletion. A
  profile rename does not rewrite past tickets — a ticket keeps the name it
  was issued under.
* `organizerId` is copied on the reservation so the organizer's queries
  (per event, and all events for statistics) are provable by security rules
  without a `get()` per document.
* The ticket code is derived from the reservation id, never stored.
* Search and category filter are client-side (small catalogue, no
  full-text index required). Swap `filteredEventsProvider` for a server
  query when the catalogue grows.

## Code generation

`freezed` (entities, DTOs), `json_serializable` (DTOs), `riverpod_generator`
(providers). Run `make gen` (or `make watch`) after editing annotated files.
Generated files are committed so CI and reviewers see real diffs.

## Design system

The "Aurora" design system is token-driven and ships **both** a light and a
dark theme (default: follow the OS, persisted override in Settings).

* `app/theme/app_palette.dart` — raw colour ramps. The only place in the
  codebase where a hex literal is allowed.
* `app/theme/app_tokens.dart` — `AppTokens`, a `ThemeExtension` mapping those
  ramps to semantic roles (`surface`, `border`, `danger.fg`, `brandGradient`,
  shadow recipes…). Widgets read `context.tokens`, never a palette.
* `app/theme/app_spacing.dart` — 4 pt spacing scale, radius scale (6 px for
  every control and modal sheet), sizes, breakpoints. `app_motion.dart` —
  durations and curves.
* `app/theme/app_typography.dart` — Plus Jakarta Sans (display) + Inter (UI).
* `app/theme/app_theme.dart` — builds `ThemeData` from a token set; light and
  dark are literally the same code over two token instances.
* `core/widgets/` — the component library, re-exported by the
  `design_system.dart` barrel.

Full rationale in `docs/DESIGN_SYSTEM.md`.

## Flavors

`FLAVOR` is a compile-time `--dart-define` (`dev` | `staging` | `prod`).
`MOCK=true` forces the in-memory backend. `USE_EMULATORS=true` points
Auth/Firestore/Storage to the local emulator suite (`firebase.json`). See
`.vscode/launch.json` and the `Makefile`.

## Testing strategy

| Layer        | How                                                             |
|--------------|-----------------------------------------------------------------|
| domain       | pure unit tests: policies, entities, drafts, ticket code, CSV, organizer insights |
| core         | `Result` / `guard` behaviour                                    |
| routes       | `RouteGuard` as a pure function — one test per rule             |
| presentation | widget + golden tests with `ProviderScope` overrides + `mocktail` repos |
| rules        | `@firebase/rules-unit-testing` against the emulators (`make test-rules`) |
| data         | integration tests against the Firebase emulator (to add)        |
