# EventHub — Architecture

Feature-first, clean-layered Flutter application backed entirely by Firebase.
The French, product-level overview is the root [`README.md`](../README.md);
this document is the technical reference.

## Dependency rule

```
presentation ──▶ application ──▶ domain ◀── data
```

* `domain` is pure Dart: entities, policies, calculators, repository
  interfaces. No Flutter, no Firebase.
* `data` implements the interfaces and is the only feature layer importing
  Firebase SDKs. `core/analytics` and `core/firebase` are infrastructure.
* `application` composes repositories into providers and controllers
  (`Future<Result<T>>` + in-flight `AsyncValue`). Controllers also emit
  analytics events on success.
* A feature never imports another feature's `data` layer; it composes its
  providers instead (check-in reads reservations through
  `reservationRepositoryProvider`, waitlist reads `myReservationForEventProvider`).

There is no simulated backend. Local development uses the emulator suite
(`USE_EMULATORS=true`). `bootstrap()` shows an error screen when Firebase
cannot be initialised.

## Error handling

Repositories never throw; `guard()` maps exceptions through `ErrorMapper`:

* `FirebaseAuthException` → `AuthFailure` (including `cancelled` for a closed
  Google picker, `accountExistsWithDifferentCredential`, `requiresRecentLogin`);
* callable functions (`plugin == firebase_functions`) → the server's French
  `HttpsError` message, `failed-precondition` as a `BusinessRuleFailure`;
* Firestore/Storage codes → `PermissionFailure`, `NetworkFailure`,
  `NotFoundFailure`, `StorageFailure`, `UnexpectedFailure`.

`AppLogger.error` forwards to `AppLogger.reporter` (Crashlytics on mobile).

## Domain rules

| Rule | Where |
|---|---|
| Booking: one per participant, not full, not started | `ReservationPolicy` (in transaction) + rules |
| Re-booking after cancellation | rules: recent `reservedAt`, cleared `cancelledAt` |
| Publishing requires a verified email | `EventFormController` + rules `isVerified()` |
| Deleting an event requires no seats taken | `EventPolicy.canDelete` + rules |
| Capacity never below seats taken | `EventPolicy.availablePlacesAfterCapacityChange` + rules |
| Waitlist: participant, sold out, upcoming, no seat | `WaitlistPolicy` + rules |
| Review: attendee, started, verified, 1–5, ≤ 2000 | `ReviewPolicy` + rules |
| Door admission | `CheckInPolicy` (pure) + append-only rules |
| Account deletion cascade | `deleteAccount` Cloud Function |

Pure calculators: `Reservation.ticketCode/ticketPayload`, `TicketPayload.parse`,
`GuestListCsv`, `OrganizerStats`, `OrganizerAlerts`, `ReviewSummary`,
`mergeCatalogue`, `NotificationRoute`, `NotificationPreferences`.

## Authentication

* `watchSession()` is built on `userChanges()` (so an email-verification reload
  reaches the UI), `distinct` on uid + `emailVerified`, `switchMap` onto the
  Firestore profile, with a grace period before `ProfileMissing`.
* `AppUser.emailVerified` comes from Firebase Auth, never from Firestore.
* Google Sign-In 7: native picker → ID token → `GoogleAuthProvider.credential`;
  web: `signInWithPopup`. A first Google sign-in has no profile →
  `ProfileMissing(displayName)` → role choice on `/complete-profile`.
* After the profile appears, the repository waits for the `role` custom claim
  (`setRoleClaim`) and refreshes the token.
* Sign-up sends the verification email; `refreshEmailVerification()` reloads
  and force-refreshes the token.
* Account deletion: re-authenticate (password or Google), call the
  `deleteAccount` callable, sign out.

## Navigation

Two `StatefulShellRoute`s (participant 4 tabs, organizer 4 tabs). Leaf routes
(detail, ticket, favorites, forms, participants, check-in, notification centre,
support pages) sit on the root navigator. `RouteGuard.redirect` is a pure
function; role-agnostic pages (`/welcome`, `/change-password`,
`/account/edit`, `/notifications`, `/help`, `/privacy`, `/about`) are declared
in `AppRoutes`. The router observer reports screen views to analytics.

## Catalogue pagination

Security rules cap a `list` at 100 documents. The catalogue is:

1. `upcomingEvents` — the first 100 upcoming events, **live**, ordered by
   `startsAt` then document id;
2. `CatalogueExtraPages` — older pages fetched on demand with
   `startAfter([startsAt, id])`, one-shot, reset by pull-to-refresh;
3. `catalogue` — `mergeCatalogue(live, older)`: deduplicated, live wins,
   catalogue order. Rails, search filters and category counts read it.

## Push notifications

**Server** (`functions/src/index.ts`): `notifyOrganizerOnReservation`
(booking/cancellation; also removes the booker's waitlist entry),
`sendEventReminders` (hourly, delegates to exported `runEventReminders`),
`notifyWaitlistOnSeatRelease` (seats freed → oldest waiting, one per seat,
`notifiedAt`). Each send reads `private/notifications`, writes
`users/{uid}/notifications` (TTL), pushes to `devices`, deletes stale tokens.

**Client** (`features/notifications/`): `PushNotifications` follows the
session (permission, token, refresh, foreground display, taps, `deleteToken`
on sign-out); web uses a VAPID key and `web/firebase-messaging-sw.js`.
`NotificationRoute.locationFor(data)` is the single routing function for
system notifications and the notification centre.

## Production concerns

* **App Check** — activated in `bootstrap()` (Play Integrity / App Attest in
  release, debug providers otherwise, reCAPTCHA v3 on web); callable functions
  honour `ENFORCE_APP_CHECK`.
* **Crashlytics** — fatal Flutter/platform errors and logged errors; collection
  off in debug; user id set from the session.
* **Analytics** — opt-in: collection disabled in the manifest/Info.plist,
  enabled by `AnalyticsConsent`; `AppAnalytics` never throws.
* **Offline** — Firestore persistence (100 MB cache); `OfflineAware` band.
* **Release signing** — `android/key.properties`.

## Data model

See README §6. Deterministic ids everywhere uniqueness matters; reservations
denormalise user and event fields; ticket codes are derived.

## Code generation

`freezed`, `json_serializable`, `riverpod_generator` — `make gen`. Generated
files are committed.

## Flavors and configuration

`FLAVOR`, `USE_EMULATORS`, `GOOGLE_SERVER_CLIENT_ID`, `FIREBASE_WEB_VAPID_KEY`,
`APP_CHECK_RECAPTCHA_SITE_KEY` (dart-defines); `AppConfig.functionsRegion`
must equal `REGION` in the functions — `us-central1`, because the `(default)`
Firestore database is in `nam5` and Firestore triggers must run in the
database's location.

`firebase.json` also carries the `flutter` block written by
`flutterfire configure` (app ids per platform), so `flutterfire configure`
without arguments regenerates `lib/firebase_options.dart` and
`android/app/google-services.json`, both git-ignored.

## Testing strategy

| Layer | How |
|---|---|
| domain | pure unit tests (policies, calculators, parsers) |
| core | Result/guard, ErrorMapper, AppLogger |
| routes | RouteGuard as a pure function |
| presentation | widget + golden tests with provider overrides (auth screens, startup, ticket, stats, notification centre) |
| rules | `@firebase/rules-unit-testing` on emulators (`make test-rules`) |
| functions | `node:test` integration tests on Auth/Firestore/Functions/Storage emulators (`make test-functions`) |
