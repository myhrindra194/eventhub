# EventHub — Architecture

Feature-first, clean-layered Flutter application. Every feature owns its
four layers; cross-cutting code lives in `core/` and app wiring in `app/`.

```
lib/
├── main.dart · main_dev.dart · main_staging.dart · main_prod.dart   entrypoints
├── bootstrap.dart              startup sequence (Firebase, error handlers, ProviderScope)
├── firebase_options.dart       generated by flutterfire (git-ignored)
├── app/
│   ├── app.dart                MaterialApp.router + localisation
│   ├── router/                 go_router config, role guards, route constants
│   └── theme/                  AppColors (Figma tokens) + dark-only Material 3 theme
├── core/
│   ├── config/                 Flavor, AppConfig, Clock provider
│   ├── errors/                 Failure hierarchy, ErrorMapper, FailureException
│   ├── result/                 Result<T> (Ok/Err), guard()
│   ├── firebase/               SDK providers, collection/field names, converters
│   ├── l10n/                   AppStrings (FR)
│   ├── utils/ · extensions/    logger, validators, date formats, context helpers
│   └── widgets/                AsyncValueWidget, state views, buttons, dialogs
└── features/
    ├── onboarding/             first-launch carousel, seen-once flag
    ├── auth/
    ├── events/
    ├── reservations/
    ├── organizer/              organizer-only screens (dashboard, participants)
    └── participant/            participant shell (bottom navigation)
        └── <feature>/
            ├── domain/         entities (freezed), policies, repository interfaces
            ├── data/           DTOs, Firestore/Storage data sources, repository impls
            ├── application/    Riverpod providers & controllers (use-cases)
            └── presentation/   screens & widgets
```

## Dependency rule

```
presentation ──▶ application ──▶ domain ◀── data
```

* `domain` depends on nothing but `core/result` and `core/errors`.
  No Flutter, no Firebase (`TimeOfDayValue` exists for that reason).
* `data` implements domain interfaces; it is the only layer that imports
  `cloud_firestore` / `firebase_auth` / `firebase_storage`.
* `application` composes repositories into providers. Controllers expose
  `Future<Result<T>>` **and** mirror the in-flight state in `AsyncValue`
  so screens can both `await` the outcome and render loading/error.
* `presentation` reads providers and never touches repositories directly.

## Error handling

Repositories never throw. Every method returns `Result<T>`:

```dart
switch (await repo.reserve(...)) {
  case Ok(:final value): ...
  case Err(:final failure): context.showFailure(failure);
}
```

`guard()` is the single try/catch: it maps SDK exceptions through
`ErrorMapper` into the sealed `Failure` hierarchy (`AuthFailure`,
`NetworkFailure`, `PermissionFailure`, `NotFoundFailure`,
`ValidationFailure`, `BusinessRuleFailure`, `StorageFailure`,
`UnexpectedFailure`). Inside Firestore transactions, domain rule violations
are thrown as `FailureException(failure)` and unwrapped by `guard()`.

## Business rules (domain policies)

| Rule (spec §7)                                   | Where enforced                                  |
|--------------------------------------------------|-------------------------------------------------|
| One reservation per participant per event        | `ReservationPolicy` + deterministic doc id `<eventId>_<uid>` + rules |
| No booking on a full event                       | `ReservationPolicy.canReserve` (in transaction) + rules bound check |
| No booking once the event started                | `ReservationPolicy.canReserve`                  |
| `availablePlaces` updated per reservation        | Firestore transaction (`FieldValue.increment`)  |
| Organizer edits/deletes only own events          | `EventPolicy.canManage` + `firestore.rules`     |
| Capacity cannot drop below reservations          | `EventPolicy.availablePlacesAfterCapacityChange` (in transaction) |
| Deleted event no longer bookable                 | Hard delete; reservations keep denormalised event data |

Policies are pure Dart and fully unit-tested (`test/features/*/domain`).
They run **inside** the Firestore transaction so two concurrent bookings of
the last seat cannot both succeed. `firebase/firestore.rules` re-checks the
invariants server-side for tampered clients.

## Authentication session

`authSessionProvider` (kept alive) exposes a sealed `AuthSession`:

* `SignedOut`
* `SignedIn(AppUser)` — Firebase user **and** Firestore profile present
* `ProfileMissing(uid, email)` — account without profile document; the
  router sends it to `/complete-profile`. A grace period
  (`AppConfig.profileGracePeriod`) absorbs the sign-up window between
  `createUser` and the profile write.

The router's `refreshListenable` is notified on every session change, so
role-based redirects run without rebuilding `GoRouter`.

## Data model (Firestore)

```
users/{uid}                 name, email, role, createdAt
events/{id}                 title, description, imageUrl?, category, startsAt,
                            location, capacity, availablePlaces,
                            organizerId, organizerName, createdAt, updatedAt
reservations/{eventId_uid}  eventId, userId, organizerId, userName, userEmail,
                            eventTitle, eventStartsAt, eventLocation,
                            status (confirmed|cancelled), reservedAt, cancelledAt?
```

Design decisions:

* `date` + `time` from the spec are stored as one `startsAt` Timestamp
  (exact ordering, "upcoming" query, "already started" rule). The `Event`
  entity exposes `date` / `time` views.
* Reservations denormalise user and event fields: the participant list and
  "Mes réservations" render with a single query and survive event deletion.
* `organizerId` is copied on the reservation so the organizer's participant
  query is provable by security rules without a `get()` per document.
* Search and category filter are client-side (small catalogue, no
  full-text index required). Swap `filteredEventsProvider` for a server
  query when the catalogue grows.

## Code generation

`freezed` (entities, DTOs), `json_serializable` (DTOs), `riverpod_generator`
(providers). Run `make gen` (or `make watch`) after editing annotated files.
Generated files are committed so CI and reviewers see real diffs.

## Design system

The "Aurora" design system is token-driven and ships **both** a light and a
dark theme (default: follow the OS, persisted override in Settings).

* `app/theme/app_palette.dart` — raw colour ramps. The only place in the
  codebase where a hex literal is allowed.
* `app/theme/app_tokens.dart` — `AppTokens`, a `ThemeExtension` mapping those
  ramps to semantic roles (`surface`, `border`, `danger.fg`, `brandGradient`,
  shadow recipes…). Widgets read `context.tokens`, never a palette.
* `app/theme/app_spacing.dart` — 4 pt spacing scale, radius scale, sizes,
  breakpoints. `app_motion.dart` — durations and curves.
* `app/theme/app_typography.dart` — Plus Jakarta Sans (display) + Inter (UI).
* `app/theme/app_theme.dart` — builds `ThemeData` from a token set; light and
  dark are literally the same code over two token instances.
* `core/widgets/` — the component library, re-exported by the
  `design_system.dart` barrel.

Full rationale in `docs/DESIGN_SYSTEM.md`.

## Flavors

`FLAVOR` is a compile-time `--dart-define` (`dev` | `staging` | `prod`).
`USE_EMULATORS=true` points Auth/Firestore/Storage to the local emulator
suite (`firebase.json`). See `.vscode/launch.json` and the `Makefile`.
